## 已核实的设计特征

1. 服务商配置与模型条目分离。服务商有稳定 ID、显示名称、服务地址、协议、凭据引用与模型列表。
2. API Key 通过专用凭据接口存储，普通配置保存引用；界面呈现是否配置等状态，不读回展示密钥。
3. 基础配置优先，服务地址、模型能力等放在可展开区域；模型条目可声明真实 ID、显示名、上下文容量、输出限制和输入类型。
4. 自定义接口的协议选择明确列出 OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages；地址如何拼接取决于协议，不能仅凭服务地址判断。
5. 支持手动声明模型和从接口发现模型；发现结果先由用户选择，再写入配置。不能假定所有服务都支持发现模型。
6. 模型原始 ID 与显示名称分开，保存及调用保持原始 ID。
7. 地址格式、唯一 ID、模型字段等在保存前校验；编辑失败保留编辑状态与诊断。
8. 保存服务或凭据不应无意改变已选择模型。配置写入带版本校验以识别冲突。
9. 推理能力属于模型能力，不能假设同一服务下每个模型都支持同样的推理参数。
10. DSH 的凭据引用分离不等于凭据天然加密；其本地凭据存储文档也明确说明同一 OS 用户进程的访问边界。Obsidian 双端需独立验证凭据方案。

## 本项目的候选设计，尚未全部被用户确认

- 将 DSH 的服务商与模型结构转为适合 Obsidian 的配置模型，通过小型适配器隔离网络协议。
- 保留手动填写模型作为模型发现失败或不支持时的路径。
- 配置状态、模型列表读取成功、最小调用成功分别呈现，避免将“填好了”误当作“已能使用”。
- 凭据存储与可同步的普通配置解耦；实际双端存储能力、用户是否需每台设备配置密钥需单独验证。
- 仅展示已实现且经过验证的协议；DSH 支持某协议不构成本插件已支持的证据。
- 首版以文本为主，图片、OAuth、桌面环境变量链和 DSH 自有插件框架均非当前明确需求。
